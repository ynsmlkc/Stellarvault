Approve as a team.
Reveal nothing.

The first confidential multi-signature treasury on Stellar. Every transaction can be transparent — or private — and you decide, per transaction, what the chain is allowed to see.

01 — The problem

A public ledger tells everyone everything.

Stellar already has multi-sig — natively, and through LOBSTR Vault, Solar, StellarGuard. Every one shares the same two limits.

Fully transparent

Every fund movement reveals who proposed, who approved, how much, and to whom. For payroll, OTC deals, grants or treasury rebalancing, that leaks salaries, strategy and counterparties.

Native = not programmable

Native multi-sig is a fixed protocol feature — signers, weights, thresholds, nothing more. No custom on-chain logic: no spending limits, time-locks, modules, or zero-knowledge.

There is no confidential multi-sig on Stellar, and no programmable one. That is the gap.

02 — The solution

Same vault, same threshold — two privacy levels.

A Soroban smart-contract multi-sig where the initiator picks privacy per transaction. The same approval, recorded two different ways:

Transparent Alice ✓   Bob ✓ → 10 XLM → GXYZ… Public ledger
Private · ZK nullifier · 0x9f3c…a71e “a valid signer approved” Identity hidden

Voter privacy hides who approved. A separate shielded pool hides amount + recipient and severs the deposit↔recipient link entirely.

03 — How it works

One flow. You choose the mode at step two.

STEP 01

Propose

propose()

Any signer proposes a transfer and picks transparent or private mode.

→
STEP 02

Approve

approve() · approve_zk()

Co-signers approve. In ZK mode a Groth16 proof is generated in-browser; only a nullifier hits the chain.

→
STEP 03

Execute

execute()

Threshold met → the contract moves real XLM on testnet, wallet-signed.

Double-voting is prevented by the nullifier; the signer’s identity is never recoverable from it.

04 — Why a contract, not native multi-sig

Native multi-sig counts signatures. That’s all it can do.

Stellar Vault is a Soroban smart contract — which is exactly what makes the rest possible:

  • Zero-knowledge approvals — verifying + recording a Groth16 nullifier on approval is logic a native account simply cannot execute.
  • Confidential execution — moving funds through a shielded pool needs a programmable contract.
  • A factory, one contract per vault — each vault is its own deployed contract with its own address and balance, Gnosis-Safe-style.
LOBSTR Vault is “Stellar’s signing app.”
Stellar Vault is “Stellar’s confidential, programmable Safe.”

06 — The zero-knowledge core

Prove you’re a signer — without saying which one.

  • Membership — “I know a secret whose commitment is in this vault’s signer Merkle tree.” → I’m valid.
  • Binding — the vote is tied to this exact (vaultId, txHash).
  • Nullifier — Poseidon(commitment, txHash) is a unique one-way tag → double-voting detectable, identity not recoverable.
Public inputs — all the chain sees
[ vaultId, txHash, signerRoot, nullifier ]

Everything else stays private. The on-chain ZKApprovalEvent emits only the nullifier — never the signer.

09 — How it evolved

Every fix here is a real commit, driven by real testing.

  • The big one: testing revealed every vault shared one balance → I re-architected into a Safe-style factory, one isolated contract per vault. A major rewrite driven directly by using the product.
  • A co-signer on a second account couldn’t see the shared vault → the factory now registers each vault under every signer, not just the owner.
  • “Private hides everything” was misleading → reframed honestly: private = anonymous approvals, with a separate shielded pool for amount/recipient.
  • Execute failed on RPC lag → added retries + longer polling. Approve button re-click errored → added a clear “you approved · waiting” state. Mobile → responsive layout.

10 — Where it goes

A confidential, programmable Safe for Stellar.

Roadmap

On-chain Groth16 verifier · Safe-style modules & guards (spending limits, time-locks, session keys, social recovery) · relayer / meta-tx for full approver anonymity · confidential execution wired into the vault.

Foundation

Because each vault is a programmable contract — not native multi-sig — it’s the right base for everything native multi-sig structurally can’t add.
