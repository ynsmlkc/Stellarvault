## Arbitrary contract calls (2026-08-02)

vault-instance, VERSION 3 = 239ac5861f11b4719c42b16432a74d25e1313da63a9a17aeb1fa70584cfa50dd
  factory.set_wasm applied — this is what new vaults get now.
  Adds propose_call / allow_contract / revoke_contract / get_allowed_contracts
  / get_call. Multi-asset falls out of it: a token the vault was not created
  with is just another contract to call.

Guards on this path: the threshold and the time-lock apply; the amount limits
cannot, because a call carries no amount the contract can read. The call
allowlist stands in for them, and starts EMPTY — a fresh vault cannot call
anything until the owner names targets.

The vault can never be its own call target. Refused both when allowlisting and
when proposing: otherwise one passing proposal could call set_policy, add_signer
or upgrade, and lift every guard it was subject to.

  - propose_call with an empty allowlist -> Error(Contract, #27)

## Real signer secrets + anonymous approval (2026-08-03)

vault-instance, VERSION 4 = 4cf255ce91af7c924648bc70a1e7580ade9bee95324710d83584459472c2df3a
  factory.set_wasm applied — this is what new vaults get now.
  Adds set_signer_commitments / get_signer_commitments and approve_zk_anon.

Two defects in the anonymous-approval feature, both fixed here:

  1. The signer secret was derived from the signer's public ADDRESS, so every
     input to the commitment was public and an observer could compute
     Poseidon(commitment, txId) per signer and match the published nullifier.
     Reproducing a real testnet approval's nullifier from public data alone
     confirmed it. Keys now come from a wallet signature (Ed25519, so
     deterministic — regenerated on demand, never stored).

  2. approve_zk called require_auth on the signer and took their address as an
     argument, so the transaction named the approver twice. approve_zk_anon
     takes no address and calls no require_auth: the proof is the
     authorization. Refused unless verification is enabled.

Leaves are published SHUFFLED. A prover needs every leaf for its Merkle path,
so the list must be public — but in signer order it would hand back the exact
mapping fix (1) removes.

Verified on testnet, vault CBTULRSDGSBY4LRDCY67FB46LG4YYLSFXNIOZY7UDC6J2QBLOUF2SCXQ:
  - commitment from signature != the value derived from the public address
  - a wallet that is NOT a signer submitted a valid approval; it counted, and
    the ledger records only that submitter

Reproduce: cd circuits && DEPLOYER_SECRET=… STRANGER_SECRET=… \
             node e2e-anon.mjs <vault> <verifier>

First vault from the upgraded factory: CD6KZV2ZVXTD7PERRTCPPMNHKPH6ZPFMZ72PSPGDQO3COJSBWORJQ4K2
  version() = 4, no zk config, no published signer set — safe defaults.

NOTE: the new key derivation is incompatible with the old one. A vault that had
verification enabled before this must republish its signer set, or its members'
proofs will no longer verify.

--- 2026-08-09 · factory get_wasm (INCIDENT: a vault was downgraded v5 -> v4) ---
factory wasm 428558e9ee4b1b753f1a7ffe95a210e1d4d322b5e42f300ccf4c8c8a56d512f1

What happened: `next dev` reads .env / .env.local, not .env.production, and only
the tracked .env.production was updated after each deploy. The dev app therefore
proposed an upgrade to the hash it had — d4557e7a, the v4 build — and the vault
CBMMPQNW5WSS7XVEHIXCX5UDCW3IUT5RWYWG5E5E5FWHFBVBNWBUCRFL went from v5 to v4.

The upgrade worked exactly as designed. That is the point: naming the wrong hash
does not fail, it installs old code, and no guard in the vault can tell one
build from another.

Fix: the factory now exposes `get_wasm`, and the app reads the target from chain
at the moment of upgrading instead of from a build-time copy. The proposal also
shows the FULL hash, since a signer approving it has nothing else to check.

All three env files are now in step, and the dev ones are the ones that matter
for anything run locally.

The 1-stroop row is why line items use formatXLMExact: formatXLM cuts at two

v10 + v11 — the guards, and who is allowed to satisfy them
================================================================================

Two security rounds, deployed together. WASM
  a4f4718f57d4984457d53187e94825ac76ebc24db3d8080812cf72410209afa6
uploaded  tx d2fbf5ec78938439222f2fbaed75e56b31013691a830ca5707997aa4965a349d

`get_wasm` on CA3VDWIX… now returns it, so the app's upgrade button targets v11.

v10 — one signer, one approval. `approval_count` is one number, but the guards
protecting it were three ledgers that never consulted each other:
`approve` -> DataKey::Approval(tx_id, signer); `approve_zk` and
`approve_zk_anon` -> DataKey::Nullifier only. A single signer reached any
threshold three ways: two made-up nullifiers with no verifier configured (which
is every vault the factory deploys), a transparent approval plus their own
legitimate proof, or the same proof replayed as `n` and `n + r` since
Bn254Fr::from_u256 reduces mod r silently. Proven in the test host first — one
signer moved the whole balance, thief_balance=1000 — then closed and proven
again at 0.

v11 — the guards guard. A call proposal walked past every spending limit
because the branch returned before them; the amount is now measured across the
invocation and charged. The time-lock ran from `created_at`, so a proposal
older than the lock settled the instant it hit threshold; it runs from the last
approval. The cap window was an absolute bucket, so "1M per day" meant 2M
across a boundary; it opens at the first spend. Duplicate signers were accepted
and could strand a vault below its own threshold. SetZkConfig and
SetSignerCommitments did not retire open proposals.

Verified live on CDO5MM5RA46SQMTAIPTPRCZYJ3UGNHHUJA6D4K35ONI3N2DDZTGLEBPL
(2-of-2, throwaway keys, no user funds):

  version()                                    -> 11

     approve_zk(A, nullifier=187)  same signer -> Error(Contract, #8)  AlreadyApproved

Existing vaults stay on the code they were deployed with. A vault still on v9
now reports two gaps in the app's upgrade notice rather than one.

v12 + v13 — the half-fixes finished, and the clock the lock runs on
================================================================================

WASM      3109f7f4946c1ed806479f47443208bd34d7b2ca3d8fd8cb303b59cde01d78de
uploaded  tx 7fdbab2c54703ed2a479a874d1ae971b2307765fc64cca6c6b648af7fa592dbe
factory   tx c334f6ed28f55b2454277130a40c9cd13bc993ee341061582865ecec0e40e30d

The first set_wasm attempt returned "transaction submission timeout". It had
not landed — `get_wasm` still read the v11 hash 20s later — and the retry above
is what took. Worth recording because the operation is idempotent, so a
timeout here is safe to retry; a timeout on create_vault would not be.

v12 closed three guards v11 had only half-fixed. The v11 commit named the four
checks the call branch skipped and closed two of them, so a call could still
pay an address the recipient allowlist refused. The cap window was anchored to
the first spend, which moved the boundary rather than removing it — the spender
places it, so 1 stroop opens a window, 999 fills it, and one ledger later the
whole cap is free again; it is a sliding-window counter now, and it seeds
itself from the pre-v11 DataKey::Spent bucket so an upgrade no longer returns a
budget already spent. And the duplicate-signer check had gone into
__constructor, which does not run on an upgrade — the removal guard now counts
the set it actually leaves behind.

v13 put the time-lock on the right clock. It was restamped on every approval,
so each one past the threshold bought another full lock period and a signer who
could not block a proposal could postpone it by approving it. And a proposal
that never met its old threshold had no moment of passing recorded at all, so
lowering the threshold made it pass and become executable in the same instant.

Verified live on CB6SGXQVXKDCDSXCWDUXMUVN4X4DLRUJ7PKOQ5YEASW5T3EPIOAN4LKX
(throwaway keys, no user funds), grown from 2-of-2 to 2-of-3:

  version()                                     -> 13

                                                   refused at propose, so a doomed
                                                   proposal never collects approvals
  allowlist_only on, one address allowed:
    propose(stranger, 500)                      -> Error(Contract, #17) RecipientNotAllowed
    propose_call(token,"transfer",[v,stranger,500])
      accepted as a call, approved 2-of-2,
      execute                                   -> Error(Contract, #17) RecipientNotAllowed
    vault balance before/after                  -> 5000 / 5000

  time-lock 12 ledgers, proposal #6:
    passed 2-of-2 at ledger 4122643             -> unlock_ledger 4122655  (= +12)
    execute immediately                         -> Error(Contract, #16) TimelockActive
    a THIRD approval at ledger 4122648          -> approval_count 2 -> 3,

    execute at 4122662                          -> ok, balance 5000 -> 4900

The third approval is the whole point: under v11 it would have pushed the
unlock to 4122660. The lock now starts when the proposal passes and later
approvals leave it alone.

Not covered live, only by unit test: the sliding window's fade across a
boundary, the legacy-bucket seeding on upgrade, and the threshold-change clock
reset. Each needs ledger control the network does not give.
