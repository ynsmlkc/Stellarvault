## Arbitrary contract calls (2026-08-02)

vault-instance, VERSION 3 = 239ac5861f11b4719c42b16432a74d25e1313da63a9a17aeb1fa70584cfa50dd
  factory.set_wasm applied — this is what new vaults get now.
  Adds propose_call / allow_contract / revoke_contract / get_allowed_contracts
  / get_call. Multi-asset falls out of it: a token the vault was not created
  with is just another contract to call.

Guards on this path: the threshold and the time-lock apply; the amount limits
cannot, because a call carries no amount the contract can read. The call
allowlist stands in for them, and starts EMPTY — a fresh vault cannot call
anything until the owner names targets.

The vault can never be its own call target. Refused both when allowlisting and
when proposing: otherwise one passing proposal could call set_policy, add_signer
or upgrade, and lift every guard it was subject to.

Verified on testnet, isolated vault CCSB7RF5ZC646D4YQI26DPPUQ7A54IVLJJ4EDOBH5Z34HYVVMTRRPQFV:
  - propose_call with an empty allowlist -> Error(Contract, #27)
  - allow_contract(self)                 -> Error(Contract, #28)
  - allowed call: the vault invoked the XLM SAC's transfer AS ITSELF, moving
    3 XLM out of its own balance, emitting CallExecutedEvent

First vault from the upgraded factory: CAXGKR2ZCQFEZ67IDIAFPHR6KD4BFVSS3HAZOFALODUVHRSBBKOHULZN
  version() = 3, empty call allowlist, no zk config — i.e. safe defaults.

## Real signer secrets + anonymous approval (2026-08-03)

vault-instance, VERSION 4 = 4cf255ce91af7c924648bc70a1e7580ade9bee95324710d83584459472c2df3a
  factory.set_wasm applied — this is what new vaults get now.
  Adds set_signer_commitments / get_signer_commitments and approve_zk_anon.

Two defects in the anonymous-approval feature, both fixed here:

  1. The signer secret was derived from the signer's public ADDRESS, so every
     input to the commitment was public and an observer could compute
     Poseidon(commitment, txId) per signer and match the published nullifier.
     Reproducing a real testnet approval's nullifier from public data alone
     confirmed it. Keys now come from a wallet signature (Ed25519, so
     deterministic — regenerated on demand, never stored).

  2. approve_zk called require_auth on the signer and took their address as an
     argument, so the transaction named the approver twice. approve_zk_anon
     takes no address and calls no require_auth: the proof is the
     authorization. Refused unless verification is enabled.

Leaves are published SHUFFLED. A prover needs every leaf for its Merkle path,
so the list must be public — but in signer order it would hand back the exact
mapping fix (1) removes.

Verified on testnet, vault CBTULRSDGSBY4LRDCY67FB46LG4YYLSFXNIOZY7UDC6J2QBLOUF2SCXQ:
  - commitment from signature != the value derived from the public address
  - a wallet that is NOT a signer submitted a valid approval; it counted, and
    the ledger records only that submitter

Reproduce: cd circuits && DEPLOYER_SECRET=… STRANGER_SECRET=… \
             node e2e-anon.mjs <vault> <verifier>

First vault from the upgraded factory: CD6KZV2ZVXTD7PERRTCPPMNHKPH6ZPFMZ72PSPGDQO3COJSBWORJQ4K2
  version() = 4, no zk config, no published signer set — safe defaults.

NOTE: the new key derivation is incompatible with the old one. A vault that had
verification enabled before this must republish its signer set, or its members'
proofs will no longer verify.

--- 2026-08-09 · vault-instance v7 (a signer change retires open proposals) ---
wasm hash    060f00c8f5d27c765de156e7398fbf9da8ea3c025588684f3bea34dfc80dff6b
test vault   CDMHFDPIOAXXWNYJMOUBVK5MLOKOCNGDWP5YMS7HY37YMAPRTYB2HKDD  (2-of-3)

`approval_count` is a plain counter, so an approval given before a signer left
kept counting after: a 2-of-3 vault could execute on one current signer plus the
departed one's vote. An instance-level epoch, bumped by AddSigner/RemoveSigner
and recorded on each proposal, retires them instead.

Recounting approvals against the current signer list was measured and rejected:
it is affordable (485k -> 548k CPU at 3 signers, 501k -> 932k at 16, against a
100M limit) but an anonymous approval records a nullifier and no address, so
there is nothing to recount it against. It broke the ZK path outright.

Verified live on the test vault above:
  propose payment #0, deployer approves            -> 1 of 2
  propose+pass RemoveSigner(deployer)
  signer1 approves payment #0                      -> Error(Contract, #32)
                                                      balance unchanged

--- 2026-08-09 · factory get_wasm (INCIDENT: a vault was downgraded v5 -> v4) ---
factory wasm 428558e9ee4b1b753f1a7ffe95a210e1d4d322b5e42f300ccf4c8c8a56d512f1

What happened: `next dev` reads .env / .env.local, not .env.production, and only
the tracked .env.production was updated after each deploy. The dev app therefore
proposed an upgrade to the hash it had — d4557e7a, the v4 build — and the vault
CBMMPQNW5WSS7XVEHIXCX5UDCW3IUT5RWYWG5E5E5FWHFBVBNWBUCRFL went from v5 to v4.

The upgrade worked exactly as designed. That is the point: naming the wrong hash
does not fail, it installs old code, and no guard in the vault can tell one
build from another.

Fix: the factory now exposes `get_wasm`, and the app reads the target from chain
at the moment of upgrading instead of from a build-time copy. The proposal also
shows the FULL hash, since a signer approving it has nothing else to check.

All three env files are now in step, and the dev ones are the ones that matter
for anything run locally.

--- 2026-08-09 · vault-instance v8 (retired proposals are visible and clearable) ---
wasm hash    748f8a8d0c37d9c799bc142065a30c7912bdeee438640b2f2e13601a0ec12275
test vault   CAWHK5PGJFE2THOVLWQDKB7A4SDANWAMEAKHKGTJFA7RZ3A7XD36OSDF  (2-of-3)

v7 retired proposals correctly and then left them sitting in the pending list
forever: nobody could approve them, and only the proposer could cancel — very
often the person who had just been removed.

`retired_before` is now a single watermark on the vault (the next tx id at the
moment of the signer change), replacing the per-proposal epoch stamp. Nothing is
written or read per proposal, and the UI marks the whole list from one number.
Any current signer can clear a retired proposal; a live one is still the
proposer's alone, since clearing must not become a veto.

Verified live on the test vault above:
  signer2 proposes #0 and approves it
  RemoveSigner(signer2) passes            -> retired_before = 2
  deployer (a different signer) cancels #0 -> cancelled = true

--- 2026-08-09 · vault-instance v9 (an upgrade retires open proposals) ---
wasm hash    2e197df19eb818dc0e8a83f589e467ead10f7ae1c85e7b6c9b0440c18c0ef571
test vault   CAWHK5PGJFE2THOVLWQDKB7A4SDANWAMEAKHKGTJFA7RZ3A7XD36OSDF

Found on a live vault (CBMMPQNW…, TEST 1): v7 recorded retirement per proposal
under DataKey::Epoch, v8 replaced that with the RETIRED watermark, and upgrading
between them orphaned the old record. Proposal #8 — made and approved by a
signer who was later removed in #9 — went back to being live, because v8 read
RETIRED, found nothing, and reported retired_before = 0.

v9 makes AdminAction::Upgrade retire open proposals before swapping the code.
New code can redefine what any stored value means, so nothing approved under the
old rules should carry into the new ones.

FORWARD-LOOKING ONLY. An upgrade is executed by the code that is running, so
v8 -> v9 does not retire; v9 -> v10 will. Verified on the test vault:
  v8, payment #2 with 1 approval, upgrade to v9 -> retired_before unchanged (2)
  then AddSigner on v9                          -> retired_before = 5
  execute #2                                     -> Error(Contract, #32)

A vault already carrying orphaned state clears it with any signer change, which
sets the watermark to the current tx id.
